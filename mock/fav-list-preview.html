お気に入りから検索 — 入口と一覧のモック

メニューパネルの「一覧から検索」（現在は 都道府県 / 城主 / 遺構 の3本、 .nearby-list-btns は repeat(3, 1fr)）に、 星のボタンを足して「お気に入り一覧」へ入れるようにする案。 枠は iPhone SE3 の 375px 幅で、寸法と色は index.html の実物から写している。 マークの3種類と行のバッジは mock/fav-badge-preview.html の 「一覧・案1（アイコンの右上にバッジ）」を採った前提。

2. お気に入り一覧ビュー

城主一覧・都道府県一覧・遺構一覧と同じ枠組み（.lords-head ＋ .lords-filter ＋ .lords-scroll）の、メニューパネル内の新しいビュー。 下のチップは実際に動くので、絞り込みと並べ替えの効き方を確かめられる。

お気に入り

種別（食べログ・お城…）の絞り込みチップは置いていない。設定の「オブジェクト表示」で消した種別は 地図・検索・周辺検索・都道府県から探す・城主から探すの全部から消える決まりなので、 お気に入り一覧もそれに従わせる（この画面だけ別の種別セットを持たせると規則が二重になる）。

3. 一覧からオブジェクトへ飛ぶ／戻る

行をタップしたときの動きは、県ページの prefJumpToItem() と揃える。 saveListReturnCamera() で今の地図を控える → closeNearby() → onResultClick(item) で寄せて情報シートを開く → 400ms 後に戻り導線を挿す、の順。 戻ると地図も一覧のスクロール位置も飛ぶ前へ戻る。

5. 保存の形（いまはローカル、後でサーバー）

保存先だけ差し替えられるように、読み書きを2つの関数に閉じ込めておく。 いまは localStorage（既存の settingsState ・ nearbyTypeFilterOff と同じ置き場）で、後からサーバーに移すときは この2つの中身だけを差し替える。

種別キーの作り方根拠
食べログshop:{properties.url} 店舗ページのURLが1店1つ。data.js の全件が持つ
道の駅michi:{properties.id} 公式の駅ID（michi.js の "id": "18786"）
ポケふたpokefuta:{properties.id} 公式の連番（pokemon.js の "id": 445）
マンホール（蓋）manhole:{cardCodeKey(cardId)}、無ければ座標 カードIDは既に cardCodeKey() で正規化している。 IDを持たない蓋があるので座標へ落とす経路が要る
カード配布mhcard:{cardKeyOfCardRecord(p)} 既存の関数がそのまま使える。同じカードを複数箇所で配る147キーは配布場所ごとに別扱い
お城castle:{name}@{lng},{lat}（座標は小数4桁） castle.js に一意なIDが無く、url も空の城が多い。 同名の城が全国にあるため名前だけでは足りず、名前＋座標で作る。 データを差し替えて座標が動くと別物になるので、 castle.js に安定IDを振るのがいちばん確実

サーバーへ移すときは wrangler.toml の Cloudflare 構成に KV か D1 を足して /api/favorites を作り、上の JSON をそのまま置く形が最短。 その場合はローカルを一次キャッシュ、サーバーを正として、 at（更新時刻）が新しい方を採る形にすれば端末をまたいでも壊れない。
