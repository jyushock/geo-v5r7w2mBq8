お気に入りの書き出し — 実装可否と出力UIのモック

地図UIのお気に入りを、TravelPlan の入力ファイル（sample/input-format.md 版1.0）として 書き出せるかを確かめ、出しかたのUIを3案並べたもの。
件数はすべて手元のデータファイル全件を数えた実測（2026-08-20）。座標の桁数と重複の判定は index.html の favKeyOf・favCoordKey と同じ式で組んである。

1. 実装できるか

実装できる。お気に入りを出すのに必要な name / lat / lng は 35,323件すべてに揃っていて、欠落は0件。TSVを壊すタブ・改行の混入も0件なので、 エスケープ処理そのものが要らない。
出力に使う材料は既に favCollect() が返している （item.coords・item.properties・お気に入りキー・枠番号・登録時刻）ので、 新しく作るのは並べ替えて文字列にする関数と、それを出すUIだけ。データファイル側の変更は不要。

1.2 座標の精度（仕様 §4.3・§5.2）

仕様は小数点以下4桁を最低ライン、5桁を推奨とし、3桁以下だと警告を出すが読み込みは続けると決めている。 どこまで当たるかを全件数えた。判定は緯度と経度の桁数の少ない方で行っている。

種別3桁以下割合内訳
食べログ00.0%全件6桁以上
道の駅00.0%全件4桁以上
ポケふた30.6%3桁ちょうどが3件
カード配布40.3%3桁ちょうどが3件、2桁が1件
マンホール655.1%3桁ちょうどが60件
お城8013.4%うち675件は度分秒がちょうど割り切れた値（下記）
合計8732.5%実質的に粗いのは最大198件（0.56%）
桁数が少ない＝精度が低い、ではない。城の座標は度分秒から変換されていて、 たとえば「丸山城 33.932777777778, 131.0」は経度が 131°0′0″ ちょうどというだけで、 値そのものは秒（約31m）の精度を持っている。
実際に 値×3600 が整数になるか（＝秒の整数倍か）で分けると、 お城の801件のうち675件はこれに当たる。残り198件が3桁ちょうど（約111m）の丸めで、 全体の 0.56% にとどまる。
さらに仕様 §4.3 は「訪問順序の決定という目的だけを見れば3桁でも結論は変わらない」と明記しているので、 この198件も順序を狂わせない。地図にピンを打ったときのズレだけの話。

1.3 仕様の列と、お気に入りの対応

仕様の列区分どこから取るか備考
name必須itemDisplayName(item) そのまま使える。食べログだけは name 全体（平均26.6字）ではなく店名だけになる
lat / lng必須item.coords[1] / [0] toFixed(5) を通して推奨桁に揃える

role任意— 出発地・帰着地の情報が無い。書き出す画面で指定させる（§4）
day任意—使わない。TravelPlan 側の自動割り当てに任せる

1.4 実装するときに引っかかる点

① データの遅延ロード。startDataLoading() は6つのデータファイルを直列で読む作りで、 favCollect() は届いた分（searchIndex）しか拾えない。 城が届く前に書き出すと、城のお気に入りが黙って落ちる。
→ 保存しているキーの数（Object.keys(favStore.items).length）と、 拾えた行数を突き合わせ、足りない間はボタンを押せなくするか「読み込み中」を出す。
② favCollect() は表示設定で絞られる。 設定で消した種別と、食べログの部門の絞り込みが効く（「設定が土台」という既存の決まり）。 このまま書き出すと、設定で消しているだけの地点がファイルから消える。
→ 書き出しは設定を無視して全件出すのが素直だと考えている。ただし既存の決まりを崩すので、 §4 の画面では件数を出して「いま何件出るか」を必ず見せる形にした。
③ ファイルの受け渡しかたは実機でしか決められない。 manifest.json は "display": "standalone"。 ホーム画面から起動した状態の iOS では、<a download> が動かないという報告が Apple 開発者フォーラムに複数ある。Web Share API でファイルを渡す方法も、 navigator.canShare({files}) が false になる報告と、iOS 15 で通るという報告が両方あって定まらない。
→ 私の側では確かめようがないので、§6 に実際に動くボタンを置いた。 このページを iPhone で開いて3つ押し、どれが通るかだけ教えてほしい。
