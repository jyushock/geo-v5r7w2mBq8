# 入力ファイル仕様

TravelPlan が読み込む地点リストファイルの仕様です。
外部アプリからこの形式で出力すれば、そのまま取り込めます。

- 版: 1.2
- 制定: 2026-08-20
- 改訂履歴: [§10](#10-改訂履歴)

---

## 1. 概要

TravelPlan は、訪問したい地点のリストを受け取り、総移動距離が最小になる訪問順序を算出します。
距離は**直線距離（Haversine による大圏距離）**で計算するため、地点ごとに**名前と座標**があれば処理できます。
住所文字列から座標を求める処理（ジオコーディング）は行いません。座標は入力側で用意してください。

### 1.1 設計原則

> **ファイルが持つのは「その場所の属性」だけです。「その旅程の都合」はアプリ上で操作します。**

同じ場所でも旅程が変われば値が変わる情報は、ファイルに含めません。具体的には以下です。

| アプリ上で指定する情報 | ファイルに含めない理由 |
|---|---|
| 出発地・帰着地 | 同じ地点リストでも、旅程ごとに起点が変わります |
| 訪問日の割り当て | ルートを見ながら決める判断です |
| 滞在時間 | 旅程を組みながら調整する値です |
| 訪問の優先度・取捨選択 | 同上 |

この結果、**1つの地点リストファイルを複数の旅程で使い回せます。**
「行きたい場所リスト」を資産として蓄積し、旅程はその都度アプリ上で組む、という運用になります。

### 1.2 ファイルの単位

- 1ファイル = 1つの地点リスト
- 行数の上限はありません（地点数に応じて厳密解と近似解を自動で切り替えます）
- 同じ地点を複数のファイルに分けて管理しても構いません

## 2. ファイル形式

| 項目 | 指定 |
|---|---|
| 形式 | TSV（タブ区切りテキスト） |
| 区切り文字 | タブ `U+0009` |
| 文字コード | UTF-8（BOM の有無は問わない） |
| 改行コード | LF / CRLF のいずれでも可 |
| 1行目 | ヘッダ行（列名）。**必須** |
| 2行目以降 | 1行 = 1地点 |
| 拡張子 | `.tsv` を推奨（`.txt` も可） |

### CSV ではなく TSV とする理由

施設名・メモ・住所には `,` が混入し得ますが、タブが入ることはまずありません。
TSV ならクォートとエスケープの処理が出力側・入力側の双方で不要になります。

CSV しか出力できない場合は [§9](#9-csv--json-で出力する場合) を参照してください。

### 制約

- フィールド内にタブと改行を含めないでください（TSV では表現できません）
- 値の前後の空白は読み込み時に除去されます
- 空行は無視されます

---

## 3. 列の定義

**列の順序は問いません。**ヘッダ行の列名で判定します。
仕様に無い列が含まれていても無視するだけで、エラーにはなりません。

### 3.1 必須列

| 列名 | 型 | 内容 |
|---|---|---|
| `name` | 文字列 | 地点名。表示に使用します。空文字は不可。重複は許容します |
| `lat` | 数値 | 緯度。十進度。北緯が正 |
| `lng` | 数値 | 経度。十進度。東経が正 |

座標の詳細は [§4](#4-座標の指定) を参照してください。

### 3.2 任意列

省略した場合、または値が空の場合は既定値が適用されます。

| 列名 | 型 | 内容 | 既定値 |
|---|---|---|---|
| `note` | 文字列 | 自由記述。順序の計算には使用せず、画面に表示するだけです | 空 |
| `id` | 文字列 | 一意キー | 自動生成 |

#### `id`

再読み込み時に同一地点として扱うためのキーです。
出力元アプリ側で地点を管理する ID があれば、それを渡してください。
省略した場合は `name` と座標から自動生成します。
指定する場合はファイル内で一意にしてください。

### 3.3 意図的に含めない列

以下は**アプリ上で指定するため、ファイルには含めません**（[§1.1](#11-設計原則) 参照）。

- 出発地・帰着地の指定
- 滞在時間
- 訪問日
- 優先度

出力元アプリがこれらを持っていて、出力に含めてしまっても構いません。
仕様に無い列として無視されるだけで、エラーにはなりません。

## 4. 座標の指定

### 4.1 測地系

**WGS84 または JGD2011（日本測地系2011）で出力してください。**

- WGS84 と JGD2011 の差は数cm〜数十cm で、国土地理院は「実用上ほぼ同じものとして扱うことができる」としています。したがってどちらでも構いません
- **旧日本測地系（Tokyo Datum）は使用しないでください。**世界測地系とは約400m（東京付近で約450m）ずれます。これは後述する座標精度の議論を無意味にする大きさです
- 出力元が2001年以前の測量成果や古い地図データを参照している場合のみ、旧日本測地系である可能性があります

### 4.2 表記

**十進度（decimal degrees）で出力してください。**

```
OK    35.68120
NG    35°40'52.3"N     (度分秒。対応しません)
NG    N35.68120        (方位記号付き。対応しません)
NG    35,68120         (小数点にカンマ。対応しません)
```

南緯・西経は負値で表記しますが、日本国内であれば発生しません。

### 4.3 精度

緯度1度は約 111.2 km です。小数点以下の桁数と誤差の対応は次の通りです。

| 小数点以下 | 緯度方向の誤差 | 判定 |
|---|---|---|
| 2桁 | 約 1,110 m | 不足 |
| 3桁 | 約 111 m | 順序の決定には足りるが、地図表示でズレが見える |
| **4桁** | 約 11 m | **最低ライン** |
| **5桁** | 約 1.1 m | **推奨** |
| 6桁以上 | 約 0.11 m 以下 | 不要（GPS の実用精度を超えます） |

**推奨は小数点以下5桁、最低4桁です。**

経度方向の誤差は緯度が高いほど小さくなります（北緯35度で緯度方向の約0.82倍、北緯45度で約0.71倍）。
したがって緯度を基準に桁数を決めれば、経度側は自動的に足ります。

**訪問順序の決定という目的だけを見れば、3桁（約111m）でも結論は変わりません。**
順序が入れ替わるのは2地点間の距離差が111m以内という場合だけで、実際には起こりません。

それでも4〜5桁を推奨するのは、桁落ちや丸めの余地を残さないためです。
出力元が既に十分な精度を持っているなら、そこで削る理由がありません。
逆に、元データが3桁しか持っていない場合に、それを理由として出力を見送る必要はありません。

## 5. 検証ルール

読み込み時に以下を検証します。

### 5.1 エラー（読み込みを中止します）

| 条件 | 内容 |
|---|---|
| ヘッダ行が無い | 1行目が列名として解釈できない |
| 必須列の欠落 | `name` / `lat` / `lng` のいずれかが存在しない |
| `name` が空 | 空文字または空白のみ |
| 座標が数値でない | 十進度としてパースできない |
| 緯度が範囲外 | `lat` が -90 〜 90 の外 |
| 経度が範囲外 | `lng` が -180 〜 180 の外 |
| `id` の重複 | 明示指定した `id` がファイル内で重複 |
| 有効な地点が0件 | データ行が1行も無い |

### 5.2 警告（読み込みは継続します）

警告は、**読み込みは成功したが算出結果が期待とずれる可能性があるとき、その原因を先に知らせる**ためのものです。
したがって、**受け手が対処できる事象だけを警告にします。**対処のしようがない通知はノイズにしかならないためです。

| 条件 | 意図 | 受け手にできること |
|---|---|---|
| `lat` > 90 だが `lng` として妥当 | 緯度と経度の入れ替わりの検出 | 出力元を直す／その行を除く |
| 緯度が 20〜46 度、経度が 122〜154 度の外 | 桁の間違い、データ破損の検出 | 同上 |
| 同一座標の地点が複数 | 重複出力の検出 | 重複を消す／無視すると判断する |

緯度20〜46度・経度122〜154度は**日本のおおよその範囲を示す目安**です。
厳密な国境判定ではなく、桁の間違いや緯度経度の入れ替わりを検出するための緩いチェックとして使用します。
この範囲を外れても読み込みは継続します。

### 5.3 検出できないもの

**測地系の取り違えは検出できません。**
旧日本測地系の座標も日本国内の妥当な範囲に収まるため、値だけからは判別がつきません。
約400m ずれた位置に地点が並ぶことになります。出力側で担保してください。

### 5.4 座標の精度は警告しません

版 1.1 まで「小数点以下3桁以下」を警告していましたが、版 1.2 で**廃止**しました。理由は2つです。

**(1) 桁数は「表記」であって「精度」ではありません**

`35.5` という値からは、次の2つが区別できません。

| 実際の中身 | 真の誤差 |
|---|---|
| 0.1度単位に丸めた値 | 最大 ±5.5 km |
| `35°30'00"` を十進度にした値 | 最大 ±15 m |

度分秒を秒単位で持つ座標は、1秒 = 緯度で約 30.9 m の精度があり、3桁（111 m）より細かい値です。
桁数で切ると、この種の値を一律に「粗い」と判定してしまいます。

**(2) 受け手に対処のしようがありません**

元データの精度は、読み込む側では上げられません。
さらに [§4.3](#43-精度) の通り、3桁の粗さが訪問順序を変えることはありません。
知らせても実害がなく、打つ手もない通知になるため、警告の条件（[§5.2](#52-警告読み込みは継続します)）を満たしません。

桁落ちやデータ破損は、多くの場合 §5.2 の範囲チェックで検出できます。

## 6. 読み込み側で吸収する範囲

出力側で神経質にならなくて済むよう、以下は自動的に処理します。

- 値の前後の空白、タブ以外の空白文字
- 空行
- BOM の有無
- LF / CRLF の違い
- 列の順序
- 仕様に無い列の混在
- 列名の大文字小文字（`Name` / `NAME` / `name` は同一とみなす）
- 列名の別名（下表）

### 認識する列名の別名

| 正式名 | 別名 |
|---|---|
| `name` | `title`, `label`, `名前`, `名称`, `地点名` |
| `lat` | `latitude`, `緯度` |
| `lng` | `lon`, `long`, `longitude`, `経度` |
| `note` | `memo`, `comment`, `備考` |

## 7. サンプル

タブ区切りです（以下の表示ではタブが空白に見える場合があります）。

```
name	lat	lng	note
目的地A	34.98530	135.75850	午前中がすいている
目的地B	34.66780	135.50120
目的地C	34.39530	132.45530	月曜休み
```

必須列のみの最小構成も有効です。実質、これが基本形になります。

```
name	lat	lng
目的地A	34.98530	135.75850
目的地B	34.66780	135.50120
目的地C	34.39530	132.45530
```

> 上記の座標は**形式を示すためのダミー**であり、実測値ではありません。

## 8. 出力側チェックリスト

外部アプリ側で出力を実装する際の確認項目です。

- [ ] 文字コードは UTF-8 か
- [ ] 区切り文字はタブか（半角スペースや全角スペースになっていないか）
- [ ] 1行目にヘッダ行があるか
- [ ] `name` / `lat` / `lng` の3列が揃っているか
- [ ] 座標は十進度か（度分秒になっていないか）
- [ ] 座標は WGS84 / JGD2011 か（旧日本測地系ではないか）
- [ ] 小数点以下4桁以上あるか（推奨。元データが3桁までなら、そのまま出して構いません）
- [ ] 緯度と経度が入れ替わっていないか
- [ ] フィールド内にタブや改行が混入していないか

## 9. CSV / JSON で出力する場合

TSV を推奨しますが、以下も受け付けます。列の定義と座標の規約は TSV と共通です。

### CSV

- RFC 4180 準拠とします
- フィールドは必要に応じて `"` で囲み、フィールド内の `"` は `""` にエスケープします
- 文字コードは UTF-8
- 拡張子は `.csv`

### JSON

- 配列のトップレベルに、地点を表すオブジェクトを並べます
- キー名は TSV の列名と同一です
- 数値は文字列ではなく数値型で記述してください

```json
[
  { "name": "目的地A", "lat": 34.98530, "lng": 135.75850, "note": "午前中がすいている" },
  { "name": "目的地B", "lat": 34.66780, "lng": 135.50120 },
  { "name": "目的地C", "lat": 34.39530, "lng": 132.45530, "note": "月曜休み" }
]
```

## 10. 改訂履歴

### 1.2 (2026-08-20)

- **座標の精度警告（小数点以下3桁以下）を廃止。**桁数は表記であって精度ではなく、度分秒由来の値を誤って粗いと判定するため。加えて受け手に対処の手段が無い。経緯は §5.4 に記載
- **§5.2 の範囲チェックの意図から「測地系の取り違えの検出」を削除。**§5.3 の「測地系の取り違えは値から判別できない」と矛盾していた。約400m のずれが緯度20〜46度・経度122〜154度のチェックに掛かることはない
- §5.2 に**警告の位置づけ**（対処できる事象だけを警告にする）と、各警告で受け手が取れる行動を追記
- §4.3 の精度推奨は維持。ただし推奨理由を「地図上のピンのズレ」から「桁落ちの余地を残さないため」に変更（アプリ側で地図を表示しない方針が決まったため）
- §5.4「座標の精度は警告しません」を追加

### 1.1 (2026-08-20)

- **設計原則（§1.1）を追加。**ファイルは「場所の属性」のみを持ち、「旅程の都合」はアプリ上で操作するという線引きを明文化
- `role` / `stay` / `day` / `priority` の4列を**削除**。いずれも旅程ごとに変わる情報であり、アプリ上で指定する
  - この変更により、1つの地点リストを複数の旅程で使い回せるようになった
- §3.3「意図的に含めない列」を追加
- §5.3「検出できないもの」を追加。測地系の取り違えが値から判別不能であることを明記
- 上記に伴い、検証ルール・チェックリスト・サンプル・別名表から該当項目を削除

### 1.0 (2026-08-20)

- 初版

## 11. 仕様の根拠

本仕様の判断根拠となった一次情報です。

| 項目 | 出典 |
|---|---|
| WGS84 と JGD2011 が実用上同一であること、旧日本測地系との差 | [測地系 \| 国土地理院](https://www.gsi.go.jp/sokuchikijun/datum-main.html) |
| 旧日本測地系と世界測地系のずれが約400m（東京付近で約450m）であること | [測地系とは？ \| ゼンリンデータコム](https://www.zenrin-datacom.net/solution/blog/geodetic-system) |
| CSV のクォート・エスケープ規約 | RFC 4180 |

座標精度の対応表（§4.3）は、緯度1度を約 111.2 km（球面近似：`2πR/360`, `R = 6371 km`）として算出した値です。
